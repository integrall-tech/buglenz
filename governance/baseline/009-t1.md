# 009 / T1 — tráfego real do `sentry-spring-boot` contra a instância

**Data:** 2026-10-08 · **Servidor:** `main` em `fc928709` (Rustrak `v0.16.0` + pacotes 002 a 007), SQLite, debug ·
**Cliente:** Spring Boot 3.5.16, Java 21 (Temurin, container), `sentry-spring-boot-starter-jakarta`
**8.60.0** (publicado em 2026-10-07). Tráfego gravado por um proxy entre o app e o servidor.
Tudo [confirmado] por execução; a chave do DSN foi omitida.

## Configuração do app (o que um produto definiria)

`sentry.release=probe-api@1.0.0`, `sentry.environment=homolog`, `sentry.send-default-pii=false`.
Cenários: uma exceção tratada com e-mail e CPF na mensagem, `Sentry.setUser` com `id` e `email`,
`setExtra("password", …)`, um breadcrumb com e-mail, e uma exceção não capturada em outra thread.

| Aspecto | Observado |

## O que o servidor guardou (camada 2, pacote 005)

| Campo | Enviado | Armazenado |
|---|---|---|
| título da issue | `… cpf 529.982.247-25 (ana@example.com)` | `IllegalStateException: pedido recusado para cpf [cpf] ([email])` |
| `user` | `{id: u-42, email: ana@example.com}` | `{id: u-42, email: [email]}` |
| `extra.password` | `hunter2` | `[Filtered]` |
| `tags.cliente` | `acme` | `acme` |

O SDK cru envia o PII integral (`send-default-pii=false` não impede `setUser` com e-mail, `setExtra`
nem breadcrumbs): a **camada 1 do wrapper é necessária**, e a camada 2 funciona com o SDK real.

## Sessões (release health)

| Cenário | Resultado |
|---|---|
| Padrão (sem `startSession`) | nenhuma sessão enviada; log do SDK: `Session is null on scope.withSession`, `Cache dir is not set`; estatísticas do projeto vazias |
| `Sentry.startSession()` + erro tratado + erro não capturado + `endSession()` | 4 envelopes: `session ok init`, `event+session ok errors=1`, `event+session crashed errors=2`, `session crashed errors=2` |
| Release health calculado | **`total 1, crashed 2, errored 0, healthy -1, crash_free_sessions_rate -1.0`** |

**Defeito do servidor [confirmado no código]:** `SessionAggregator::ingest_session`
(`workers/session_aggregator.rs`) não guarda estado por `sid`; toda atualização com status terminal
incrementa um contador. O SDK Java envia o estado terminal duas vezes para a mesma sessão (na
queda e no encerramento), então uma sessão vira 2 crashes e `healthy` fica negativo. O SDK
JavaScript envia um terminal por sessão, por isso o pacote 006 não viu isso. Efeito prático: qualquer
SDK que repita o terminal (Java com sessão explícita, e provavelmente Android e Flutter) corrompe o
crash-free.

## Conclusões para o pacote 009

1. **O wrapper Spring Boot não liga sessões.** Em servidor de longa duração a sessão não é uma unidade
   com sentido, o SDK Java não a inicia sozinho, e ligá-la expõe o defeito acima. Release health vale
   para o front-end e para mobile.
2. O contrato do wrapper Spring Boot com o servidor está **verificado**: envelope aceito, `release`,
   `environment`, tags e scrub corretos, `mechanism` e `level` preservados.
3. A camada 1 do wrapper Spring Boot precisa remover e-mail de `user`, `extra`, e texto de breadcrumb
   antes do envio; o SDK não o faz sozinho.
4. Novo achado de servidor (**G24** do GAP): contagem duplicada de terminais repetidos por `sid`. Não
   bloqueia o piloto (sem sessões no backend), mas bloqueia confiar no release health de qualquer
   SDK que repita o terminal; entra no escopo de mobile (D3, pacotes 015 e 016) ou em pacote próprio.
